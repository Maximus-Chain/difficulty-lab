# Unconventional / real-time difficulty adjustment: RTT/TSA, PID/control theory, dual-window, emergency rules, timestamp security

Context for the reader: target chain = small merge-mined (AuxPoW) X11 Dash fork, T = 72 s, Dark Gravity Wave v3 (N=24), suffering sudden 80-99% hashrate drops (a big merge-mining pool disconnecting) plus profit switching. Local code facts (from `/home/midefos/repos/maximus/src`): `MAX_FUTURE_BLOCK_TIME = 2*60*60` (FTL = 7200 s = 100 T) in `src/chain.h`; `DEFAULT_MAX_TIME_ADJUSTMENT = 70*60` (peer-time cap) in `src/timedata.h`; DGW in `src/pow.cpp` uses 24 blocks, timespan clamps 1/3x..3x, and the inherited Dash testnet-only rule (`fPowAllowMinDifficultyBlocks`): if new block time > prev + 2 h -> powLimit; if > prev + 4*T -> prev target * 10. Research date: 2026-10-23.

## 1. RTT / TSA (difficulty depends on the current block's own timestamp)

### Takeaway
RTT/TSA is the only family that fixes a *sudden* drop within the block being mined (difficulty decays while miners wait), and it has two mature reference designs: Harding's Weibull RTT (2020, Ledger) and zawy's TSA (2018). It has also had one live production deployment: eCash "Heartbeat" (Nov 2024). eCash, however, only uses RTT as a non-consensus, Avalanche-enforced *ceiling on how fast blocks can come* (it never lowers difficulty below the DAA). So it does not address stuck chains after hashrate leaves. Consensus-level RTT that lowers difficulty requires FTL << T, monotonic timestamps, parent-chainwork comparison, and it has a documented incentive flaw ("future mining", Bissias 2020). Komodo's AdaptivePoW is the deployed example of the "lower difficulty with elapsed time" direction.

### Cited Findings

**Harding RTT (exact math)**: T. M. Harding, "Real-Time Block Rate Targeting", Ledger vol. 5 (2020) 11-19, DOI 10.5195/LEDGER.2020.195 — [PDF (chain2 repo)](https://github.com/chain2/chain2/blob/master/specifications/rtt.pdf)
- Instantaneous block rate is made a monomial of time since the previous block: λ(t) = a·t^(k−1), k > 1 (k=1 gives ordinary Bitcoin). Resulting inter-block time distribution is Weibull: F(t) = 1 − e^(−a t^k / k). The mean is forced to T by choosing a = k·[Γ(1+1/k)/T]^k. — [Harding 2020](https://github.com/chain2/chain2/blob/master/specifications/rtt.pdf)
- Subtarget at elapsed time t (what the hash must satisfy): g(t) = G(n−1) · k · Γ(1+1/k)^k · t^(k−1) / T^(k−1) = G(n−1)·const·t^(k−1). Validity: H(block n) ≤ g(t_n), with t_n = s_n − s_(n−1), the difference in *committed* timestamps. — [Harding 2020](https://github.com/chain2/chain2/blob/master/specifications/rtt.pdf)
- Next committed ("Poisson-equivalent") target: map t_n back to exponential-equivalent time u_n = a·T·t_n^k / k, then G_n = G_(n−1)·u_n/T. There is no averaging of past inter-block times: the only input is the current block's own time. G_n is validated but used for block n+1's search. — [Harding 2020](https://github.com/chain2/chain2/blob/master/specifications/rtt.pdf)
- Bias fix: full per-block retarget raises the mean to T·Γ(1−1/k). The software must use T̂ = T / Γ(1−1/k) as the "desired" time. — [Harding 2020](https://github.com/chain2/chain2/blob/master/specifications/rtt.pdf)
- Variance: block-time variance is 81% lower than exponential for k=6. With k=4 and T=600, a block with t_n = 1 s is ~80 million times harder than in the traditional system. — [Harding 2020](https://github.com/chain2/chain2/blob/master/specifications/rtt.pdf)
- Required rule changes: (a) fork choice uses the **parent's** chainwork, so siblings have equal work and a miner can't orphan a competitor with a block stamped 1 s earlier; (b) t_n > 0 enforced (strictly monotonic timestamps); (c) max allowed timestamp tightened from "now + 2 h" to "now". The paper argues miners have an incentive to stamp the latest non-future time. — [Harding 2020](https://github.com/chain2/chain2/blob/master/specifications/rtt.pdf)
- Harding explicitly says he did not formally specify an algorithm or quantify performance vs. others. — [Harding 2020](https://github.com/chain2/chain2/blob/master/specifications/rtt.pdf)

**zawy12 TSA ("Time Since Arrival"/RTT)**: issue opened 2018-11-08, retitled "TSA RTT" 2020-08-21 — [zawy12 #36](https://github.com/zawy12/difficulty-algorithms/issues/36)
- Original: D_out = D_in · t / (T + (t − T)·e^(t/(T·M))), with D_in from a baseline DAA and t = miner's timestamp − previous timestamp. M>1, 3..10 suggested; M=5 gives D_out in ~60%..135% of D_in. — [zawy12 #36](https://github.com/zawy12/difficulty-algorithms/issues/36)
- Linear approximation (M=5): adjustedT = 0.893·T; D_out = D_in / (1 + t/adjustedT/M − 1/M). Two-stage EMA form ("Update #3"): chainTarget = prevTarget·(1 + prevST/T/60 − 1/60) is the official chain value; minersTarget = chainTarget·(1 + currentST/T/11 − 1/11) is what the miner must solve. — [zawy12 #36](https://github.com/zawy12/difficulty-algorithms/issues/36)
- Summary form: sub_target = SlowASERT · [e^((t_(h+1) − t_h)/T − 1)]^(1/P). The ASERT value is "official" (used for chainwork and the next block's ASERT); the sub_target is the actual hash target and depends on the miner's own timestamp. — [zawy12 #50 Summary of Difficulty Algorithms](https://github.com/zawy12/difficulty-algorithms/issues/50)
- "Long-delay-only" variant (closest to an emergency rule): if solvetime > 6T + FTL then Diff *= 0.90^((solvetime − 6T − FTL)/T), i.e. −10% per T beyond the threshold. — [zawy12 #36](https://github.com/zawy12/difficulty-algorithms/issues/36)
- Timestamp prerequisites listed there: FTL ≈ T/4 or less (others suggested 10 s, 3T, or T); peer-time revert ≈ FTL/2 (vs. BTC's 70 min); monotonic timestamps (≥ prev+1 s); pool template refresh interval ≈ sqrt(template_delay·T·M/1.8) (≈8 s for 0.2 s delay, T=120, M=5). — [zawy12 #36](https://github.com/zawy12/difficulty-algorithms/issues/36)
- Live results (Xchange coin, Feb 2019): no solvetimes > 3.4·T; earlier claim 0 blocks > 4T vs ~9% for other algos; solvetime StdDev 0.56 vs 1. Simulation: 16 per million blocks > 4T vs ~18,000 for BTC-like constant hashrate. — [zawy12 #36](https://github.com/zawy12/difficulty-algorithms/issues/36) (self-reported by the author)
- zawy's own ranking: "TSA-RTT is by far and away the best difficulty algorithm but there is a lot of resistance". It must sit on top of LWMA/ASERT/EMA (ideally ASERT). Too-strong RTT peaks solvetimes around T and causes more orphans, and if FTL isn't small "all miners will target that limit, again causing orphans". — [zawy12 #50](https://github.com/zawy12/difficulty-algorithms/issues/50)

**Attacks / caveats on RTT**
- Selfish mining with forward timestamps: a >51% attacker setting timestamps far ahead reportedly gains ~38% more blocks, and RTT on ASERT could make this worse. Emin Gün Sirer reportedly still considered it a real attack in 2021. — [zawy12 #36](https://github.com/zawy12/difficulty-algorithms/issues/36)
- Chainwork distortion: an RTT allowing ~100x difficulty change per block "enables a selfish mining attack where a 2.6% HR will be calculated as 51% HR". Fix = correct chainwork accounting (official vs. sub-target). — [zawy12 #30 Timestamp Attacks](https://github.com/zawy12/difficulty-algorithms/issues/30)
- Timestamps near the FTL edge can split nodes and cause orphans. Self-lowering difficulty is limited by FTL, and a miner gets "at most one cheap block in a row". — [zawy12 #36](https://github.com/zawy12/difficulty-algorithms/issues/36)
- **Future-mining attack (Bissias, arXiv 2007.05991, 2020-07-12)**: a miner fixes a future time t* and grinds against the easier g(t*) before t* arrives, then releases at t*. With fraction q of the hashrate, he can win with probability > q. The paper proves a unique Nash equilibrium in which *all* miners future-mine to some τ. Consequences: block races and higher orphan rate at τ; an attacker who future-mines to τ−ε preempts others (easier censoring and double-spends); and the target no longer measures real work done. — [Bissias, "Radium: Improving Dynamic PoW Targeting"](https://arxiv.org/pdf/2007.05991)
- Radium fix: also scale the block reward with the sub-difficulty, r(t) = C·d(t)/d(T), so reward per hash is constant across t and future mining is unprofitable. It uses k=2, header-first propagation, and discards blocks whose timestamp is "drastically different" from local time. The authors claim orphan/double-spend susceptibility is similar to Bitcoin. — [Bissias 2020](https://arxiv.org/pdf/2007.05991)
- zawy: complaints that the timestamping miner lowers his own difficulty are greatly reduced if honest nodes softly enforce accurate timestamps (his selfish-mining fix below). — [zawy12 #76](https://github.com/zawy12/difficulty-algorithms/issues/76)

**Deployments**
- **eCash Heartbeat (activated 2024-11-15)**: "RTT difficulty algorithm" inspired by Harding, implemented "without changes to the base consensus rules". Blocks are additionally checked against an RTT target through Avalanche post-consensus. Each node computes the target from **its own header-receive times**, starting high and decaying to the DAA level. — [e.cash blog, 2024-11-01](https://e.cash/blog/heartbeat)
- eCash code (`src/policy/block/rtt.cpp`, 2024): RTT_K = 6; factor_i = K·Γ(1+1/K)^K / N_i^(K−1), with N = 150, 600, 2400, 6000, 9600 s for windows i = 1, 2, 5, 11, 17 blocks back. For each window, diffTime = max(1, now − headerReceivedTime[i]), target_i = prevTarget·factor_i·diffTime^(K−1). The final target = min over windows (also capped at powLimit). If the block hash fails it, the block is *parked* (`POLICY_VIOLATION`, "policy-bad-rtt"), not consensus-invalid. RTT is skipped if any of the 17 receive times is unknown (e.g. after loading from disk). Windows are primes "to avoid introducing resonant frequencies". The highest difficulty over windows applies, so "the target becomes more constrained as the window increases, but also we have some room for the DAA". — [Bitcoin ABC rtt.cpp source docs](https://www.bitcoinabc.org/doc/dev/rtt_8cpp_source.html); [rtt.cpp reference docs](https://www.bitcoinabc.org/doc/dev/rtt_8cpp.html)
- eCash code review introducing it (Sept 2024): [Phabricator D16728](https://reviews.bitcoinabc.org/D16728?id=49530)
- eCash self-reported results (Oct 10 to Dec 2, 2024 comparison): block-time StdDev fell from 919 s to 665 s (BTC 584, BCH 695). Blocks > 1 h fell from 1.61% to 0.73% (BTC 0.25%, BCH 0.74%). Mean went from 596.8 to 602.6 s. Nov 15 to Dec 10: StdDev 626 s, 0.57% > 1 h. — [e.cash blog, 2024-12-12](https://e.cash/blog/real-time-targeting-in-action-early-results-of-the-heartbeat-upgrade)
- **Komodo AdaptivePoW (`ac_adaptivepow`, 2019)**: target adjusted during block discovery, to fix "diff stranding" (hashrate spikes difficulty then leaves). Described elements: "3^delay/blocktime" (not further defined), median of recent block times, exponential decay "each new block becomes easier", and activation only after (max backdating + max future-timestamp leniency + margin). Test chain (2019-07-30): after ASIC miners left at ~1.1 MH/s and diff 1.2M, difficulty fell to 9 in 456 blocks. A single CPU then averaged ~2.17 min/block. Projection: "a 1 million fold hashrate attack will readjust ... in just 7 blocks" (not measured). — [Komodo, Adaptive Proof of Work](https://komodoplatform.com/adaptive-proof-of-work/); [Komodo Antara customizations](https://komodoplatform.com/en/docs/antara/setup/antara-customizations/)
- zawy: helped jl777 implement an RTT "on steroids" for Komodo sub-chains with 1,000,000x hashrate swings. It "stopped attackers from getting more than 2 blocks cheaply and prevented stuck chains when they left." — [zawy12 #50](https://github.com/zawy12/difficulty-algorithms/issues/50); see also [zawy12 #30](https://github.com/zawy12/difficulty-algorithms/issues/30)
- Bitcoin Cash: Harding submitted a DAA proposal in 2017 (not RTT). BCH has not adopted RTT; eCash (a BCH descendant) did. — [Ledger article search hit / e.cash](https://e.cash/blog/heartbeat); [bitcoin-ml Oct 2017](https://lists.linuxfoundation.org/pipermail/bitcoin-ml/2017-October/000413.html)

### Inferences
- **eCash's RTT does not solve this chain's problem.** It takes min(target) starting from powLimit and applies on top of the consensus DAA target, so it only *raises* difficulty for blocks that come too soon after earlier ones. It suppresses switch-mining bursts and does nothing for a stuck chain after an 80-99% drop. For drop recovery the relevant designs are zawy's TSA (both directions, ~60%-135% for M=5), the "long-delay-only" variant, Harding's full RTT, or Komodo APoW.
- eCash can use node-local receive times only because Avalanche finalization resolves disagreements. On a chain without a post-consensus layer, a receive-time rule is non-deterministic and would fork nodes. (Speculative: Dash-derived ChainLocks/LLMQ, if this fork still has them active, might play an analogous role, but nothing found confirms anyone has tried.) Any consensus RTT on this chain must use the block's own header nTime.
- **AuxPoW interaction (inference, not found in sources):** with RTT, the child-chain target depends on the child header's nTime. That header is committed by hash into the parent coinbase, so the pool can't advance nTime without rebuilding aux work. Stale aux templates mean the miner solves against an *older* timestamp, so a harder target. This is conservative for security but penalizes merge-mining pools with slow `getauxblock` refresh. zawy's template-refresh formula sqrt(delay·T·M/1.8) with T=72 implies refreshing every few seconds. Pools that refresh aux work lazily (zawy notes lazy MM pool code already reuses parent timestamps, [zawy12 #35](https://github.com/zawy12/difficulty-algorithms/issues/35)) would be systematically disadvantaged.
- Current FTL (7200 s = 100 T) is incompatible with any RTT. Under Harding's math with k=6, a timestamp 2 h ahead would make g(t) astronomically easy. All sources agree FTL must be ≲ T (Harding: "now"; zawy: T/4 or ~10 s) before RTT is considered.

### Gaps
- Aeternity's DAA: no source found linking Aeternity to RTT/TSA. Not covered.
- The Ledger journal site rejected TLS, so Harding's paper was read from the chain2 repo copy (same DOI). The chain2 reference implementation's exact integer code was not inspected.
- Komodo APoW exact code constants were not retrieved (the jl777 Medium posts were not fetched). The "3^delay/blocktime" expression is undefined in the source.
- No independent (non-eCash) analysis of Heartbeat outcomes found. No public data found on RTT with merge mining.

## 2. PID / control-theory DAAs

### Takeaway
A real published PID-style DAA exists and was deployed on mainnet: Hovland & Kučera 2017, Bismuth. It is a model-inversion plus low-pass-filtered derivative controller with a 1440-block moving average, so it is very slow (bandwidth ~3111 blocks). zawy's 2018 PID derivation concludes PID is "as good as" LWMA/EMA but not clearly better. His 2022 update says the I term is redundant with the EMA filter and proposes a PD controller with gamma-CDF error. PID is rarely deployed because EMA/ASERT already *is* essentially a P(+I) controller. A D (slope) term predicts miner behavior that profit-switchers can exploit, and it adds oscillation risk when miners have no "momentum".

### Cited Findings
- **Hovland & Kučera, "Nonlinear Feedback Control and Stability Analysis of a Proof-of-Work Blockchain"**, Modeling, Identification and Control 38(4):157-168, 2017, DOI 10.4173/mic.2017.4.1. Chain: Bismuth, Td = 60 s, mainnet from block 427,000 (Bismuth v4.2.1.9). — [MIC PDF](https://www.mic-journal.no/PDF/2017/MIC-2017-4-1.pdf)
  - Measurement: moving average of the last 1440 block times (T). Controller (Matlab, Bismuth-specific log-scale difficulty):
    `H = 2^(D/2) / (T*ceil(28 - D/16)); Dnew = 2/log(2) * log(H*Td*ceil(28 - D/16)); Kd = 10; Dnew = Dnew - Kd*(T - T1);`
    i.e. estimate hashrate H from the current average block time and difficulty (model inversion), compute the difficulty for Td, and subtract a derivative term Kd·(T − T_prev). This is followed by gain K plus a discrete integrator in feedback, a first-order low-pass with cutoff K, so G(s) = K/(s+K). — [MIC PDF](https://www.mic-journal.no/PDF/2017/MIC-2017-4-1.pdf)
  - Tuning: K = 1/720, Kd = 10. Largest closed-loop eigenvalue 0.9991 (0.9995 with Kd=0). Gain margin on K = 4.7 (13.4 dB). Closed-loop bandwidth 0.00202 rad/block = ~3111 blocks ≈ 2.16 days. Kd "significantly reduces oscillations and increases the stability margin". — [MIC PDF](https://www.mic-journal.no/PDF/2017/MIC-2017-4-1.pdf)
  - Simulated step (hashrate doubled at block 10,000): block time oscillates 39-65 s, settling time ~4000 blocks, zero steady-state error. Testnet shows stable limit cycling of difficulty between 111.98 and 112.02 (integer-difficulty quantization). Mainnet: after a hashrate drop, block time rose above 70 s while the controller lowered difficulty, and it then held ~60 s over blocks 2000-13000. — [MIC PDF](https://www.mic-journal.no/PDF/2017/MIC-2017-4-1.pdf)
- **zawy12 PID (issue opened 2018-01-14, updated 2022)**: next_target = prev_target + p/N·prev_Error + i/N·avg(Errors) + d·slope(Errors), with Error_i = target_i·(ST_i/T − 1). Work in target, not difficulty. Suggested p=1, i=−0.15, d=0.15, N=50 (also p=0.5, j=k=50). EMA reduces to a P-controller: next_target = N/(N−1)·prev_target + prev_target·(ST/T − 1)/N. — [zawy12 #20](https://github.com/zawy12/difficulty-algorithms/issues/20)
- zawy 2022 update: the error should be error = target/N·(0.5 − e^(−t/T)) (exponential-CDF based). The "I" controller is redundant to the filter. The best found was a **PD** controller with P = D = 2.6/N (N = ASERT's filter constant, 2.6 chosen to match ASERT's StdDev under constant hashrate), with the D term = gamma CDF of the prior 2 solvetimes minus the 2 before, negated. "Not absolutely clear that it is generally better than LWMA and simple EMA." — [zawy12 #20](https://github.com/zawy12/difficulty-algorithms/issues/20)
- Why PID/D terms are risky: "a PID or PD controller should not help because they are needed in cases of momentum and/or friction, and will cause oscillations if they assume there is momentum and/or friction when there is not". Also: "if it ... responds ahead of time, miners will do the opposite to exploit it." — [zawy12 #48 Oscillations in SMAs](https://github.com/zawy12/difficulty-algorithms/issues/48)
- zawy's experience with "smarter" variants: LWMA-2/3/4 "provided noticeable benefit to about 70% of the coins, all of which did not really need an improvement, and made things worse for the 30% that needed improving. If sizable oscillations were present, it would usually make them worse." — [zawy12 #50](https://github.com/zawy12/difficulty-algorithms/issues/50)
- zawy's 2023 position: "WTEMA is the only difficulty algorithm people should use", target = prior_target·(1 + t/T/N − 1/N), a first-order IIR filter ≈ relative ASERT. The 2021 framing is "WTEMA / ASERT as an RC filter". — [zawy12 #76](https://github.com/zawy12/difficulty-algorithms/issues/76); [zawy12 #72](https://github.com/zawy12/difficulty-algorithms/issues/72)
- Other control/estimation literature: Zhang & Ma, ICASSP 2020 (two-layer neural network, Ethereum data) — [arXiv 2004.10670](https://arxiv.org/pdf/2004.10670). "Analysis of Difficulty Control in Bitcoin and PoW Blockchains" (arXiv 1812.10792) derives a hashrate-estimate-based update — [arXiv 1812.10792](https://arxiv.org/pdf/1812.10792). "Unstable Throughput: When the Difficulty Algorithm Breaks" (BCH oscillations, negative-exponential filter) — [arXiv 2006.03044](https://ar5iv.arxiv.org/html/2006.03044).
- **Kalman/Bayesian**: the only Kalman proposal found is an informal 2017-06-19 Mimblewimble mailing-list sketch of a "2-state Kalman filter" (difficulty and its rate of change), with no equations or analysis. Igno Peverell replied that there is "very little research in the area". — [Mimblewimble list](https://archive.lists.launchpad.net/mimblewimble/msg00145.html)
- zawy 2025 "lowest hash" estimator (Bayesian-flavored, uses sub-block info): E = CDF(L) − 0.5 with CDF(L) = 1 − e^(−λL), λ = W/2^256; W_h = W_(h−1)·e^(−E/N); StdDev ≈ W/sqrt(2N). Proposed for estimating hashrate in fixed time periods, not a deployed DAA. — [zawy12 #86](https://github.com/zawy12/difficulty-algorithms/issues/86)
- Freicoin (2013): 144-tap FIR filter hashrate estimator — [tradecraft #3](https://github.com/tradecraftio/tradecraft/issues/3); [zawy12 #38](https://github.com/zawy12/difficulty-algorithms/issues/38)
- Garay, Kiayias, Shen, "Fast Difficulty Adjustment in Proof-of-Work Consensus" (ePrint 2026/1116, revised 2026-09-10, major revision of a CRYPTO 2026 paper): claims the first constant-time provably secure difficulty adjustment, using parallel chains plus approximate agreement across chains. Not applicable to a single-chain fork without a redesign. — [IACR ePrint 2026/1116](https://eprint.iacr.org/2026/1116)

### Inferences
- For a 99% drop, a PID based on block-time averages has the same structural limitation as any per-block DAA: no new information arrives until a block is found. At 1% hashrate the first block takes ~100·T = 2 h at T=72 s. Only RTT-type rules (or emergency rules) act *during* that wait.
- The Bismuth controller is the wrong time-scale for this chain (bandwidth ~3000 blocks vs. needed tens of blocks). It mostly demonstrates that a derivative term can damp oscillation in a slow loop.
- A Kalman filter on log-hashrate with a jump/change-point model is theoretically appealing, but no peer-reviewed or deployed design was found. Its effective behavior near steady state reduces to an EMA with adaptive gain, i.e. a dynamic-window EMA (section 3).

### Gaps
- No peer-reviewed PID DAA with tuning for small, switch-mined chains found. No production Kalman/Bayesian DAA found.
- The SPAWC 2020 "Difficulty Prediction for PoW Blockchains" (linear predictor, Ethereum) was not read in full.

## 3. Fast/slow dual-window, crossover, dynamic-window, asymmetric designs

### Takeaway
Several concrete designs exist, all from 2018-era small-coin practice: zawy's Dynamic EMA (switch N on a 3x/(1/3) trigger), Dynamic LWMA, Slipstream EMA (fast EMA within ±14% of a tempered SMA, else slow EMA), KGW's variable window, and Digishield's asymmetric limits. zawy, their author, later abandoned them in favor of plain WTEMA/ASERT/LWMA with a larger N. The reasons: false triggers (e.g., a 2x jump for 4 blocks about once per 720 blocks), oscillation amplification under on-off mining, and the need for long confirmation windows to resist timestamp manipulation.

### Cited Findings
- **Dynamic EMA** (zawy, 2017-12-06): default Nmax=140, Nmin=50. Trigger on median-of-3 timestamps: if (median(TS[i..i−2]) − median(TS[i−A..i−A−2]))/T/A > B or < C, with (A,B,C) = (11, 2.1, 0.36) or (20, 1.65, 0.45), then N = min(Nmax, blocks_since_event + Nmin). N recovers linearly back to Nmax after the event. It "needs 20 blocks out of fear of timestamp manipulation". — [zawy12 #5](https://github.com/zawy12/difficulty-algorithms/issues/5)
- **Dynamic LWMA** (2018-05-04): drawback "once every 720 blocks ... a 2x jump in difficulty for 4 blocks" by accident (false trigger). — [zawy12 #25](https://github.com/zawy12/difficulty-algorithms/issues/25); wiki [Dynamic LWMA](https://github.com/zawy12/difficulty-algorithms/wiki/Dynamic-LWMA)
- **Slipstream EMA** (2018-05-20), exact code (Cryptonote, N=60):
  ```
  ST = max(-FTL, min(ts[N]-ts[N-1], 6*T));
  next_D = D*9*T/(8*T + ST*1.058);              // fast EMA (~N=9)
  tSMA   = sumD*2*T/(N*T + sumST);              // 50% tempered SMA, N=60
  if (next_D > tSMA*1.14 || next_D < tSMA*0.877)
      next_D = D*28*T/(27*T + ST*1.02);         // slow EMA (~N=28) outside +/-14%
  return 0.9935*next_D;
  ```
  The rationale given: the fast EMA within ±14% counters ±9% miner motivation thresholds, and the slow EMA resists going far outside. The 6T solvetime cap "prevents D dropping too far after attack to prevent on-off attack oscillations". It requires FTL < 3T. Not tested on a live coin per the later summary. — [zawy12 #27](https://github.com/zawy12/difficulty-algorithms/issues/27); [zawy12 #50](https://github.com/zawy12/difficulty-algorithms/issues/50)
- **KGW** (Kimoto Gravity Well) changes window size when solvetimes are too fast or slow, but with "no justification ... for the curve". It has an out-of-sequence-timestamp exploit. Zcoin's version limited changes to once per 12 blocks, "which should cause oscillations". — [zawy12 #50](https://github.com/zawy12/difficulty-algorithms/issues/50)
- **Time-based window** (2018-01-15): window = blocks within N·T seconds (Nmax=100, Nmin=30), untested, "probably has a symmetry problem ... if not cause oscillations". — [zawy12 #22](https://github.com/zawy12/difficulty-algorithms/issues/22)
- **Auto N from StdDev of D** (2018-11-08): placeholder idea only. — [zawy12 #37](https://github.com/zawy12/difficulty-algorithms/issues/37)
- **Digishield asymmetry**: 6-block MTP delay causes "tolerable oscillations". Its 16%/32% timespan limits "force a 500 block delay in it reaching the correct solvetime if difficulty changes a lot". Zcash's 2020 MTP-based FTL change allowed exploiting the asymmetric 16%/32% limits, raising emission by ≥25%. — [zawy12 #50](https://github.com/zawy12/difficulty-algorithms/issues/50); [zawy12 #30](https://github.com/zawy12/difficulty-algorithms/issues/30)
- **"LWMA with a jump rule"**: user report (2026-04-01) of LWMA N=60 with a 3x per-block clamp, asking about long-term effects. No answer captured. — [zawy12 #88](https://github.com/zawy12/difficulty-algorithms/issues/88). zawy's general position: "Timespan limits and other methods of changing what a correct difficulty algorithm calculates should not be used." — [zawy12 #76](https://github.com/zawy12/difficulty-algorithms/issues/76)
- Oscillation mechanics relevant to switching: SMA windows ring at harmonics of N (N=144 at 144, 72, 36 blocks). Hashrate response is non-linear ("common in alts to see 3x more hashrate join when there is a 30% drop in difficulty, and it can go to 1/3 when difficulty is 30% higher"). Delays that ignore recent solvetimes create positive feedback. — [zawy12 #48](https://github.com/zawy12/difficulty-algorithms/issues/48)
- Window choice: zawy now prefers larger N (ASERT/EMA M≈144, LWMA N≈288 at T=600). Coins with large daily price swings or on-off miners "might be better off with 1/2 these values". ASERT/WTEMA difficulty StdDev ≈ 1/sqrt(2N) under constant hashrate (N=50 → 10%). — [zawy12 #50](https://github.com/zawy12/difficulty-algorithms/issues/50); [zawy12 #76](https://github.com/zawy12/difficulty-algorithms/issues/76)
- DGW-specific defects (relevant baseline): DGW's "average" double-weights the most recent target, uses 1 fewer timestamp than intended (+1/24 solvetime), and has a small-N Erlang bias. Together ~6% longer solvetime. Its 3x and 1/3 timespan limits allow unlimited blocks in ~2x window to a selfish miner if timestamps are non-sequential. — [zawy12 #31 DGW Problems](https://github.com/zawy12/difficulty-algorithms/issues/31) (2018-09-04)

### Inferences
- A fast/slow switch addresses profit-switching *bursts* (fast up-response) but does little for a sudden 99% drop. The fast window still needs a few slow blocks to observe the drop, and at 1% hashrate each takes ~100·T. The decay-during-the-block mechanism (RTT/TSA, or a gentle long-delay rule) is what bounds the first post-drop block.
- Triggered designs are exploitable by switchers who can cause the trigger (enter/leave to flip N). Slipstream's ±14% band is effectively a hysteresis band, and switchers can sit just outside it.

### Gaps
- No live-chain results found for Slipstream, Dynamic EMA, or Dynamic LWMA. The original "LWMA-2/3/4 jump rule" code (e.g. a "3 fast blocks → +x%" rule) was not retrieved; issue #33 now redirects to #3.

## 4. Emergency rules (min-difficulty after X minutes, BCH EDA)

### Takeaway
Both well-known emergency rules failed in practice. BCH's EDA (2017) created large oscillations and let BCH get thousands of blocks ahead. Bitcoin testnet's 20-minute rule produced block storms in testnet3, and in testnet4 it was being farmed (~85-90% of blocks CPU min-difficulty, 2026). The safer variants share three properties: the base difficulty never inherits an emergency value, the relief is gradual (multiplicative decay per elapsed T, not a jump to powLimit), and it triggers only after delay > (FTL + MTP slack + margin), as in zawy's long-delay TSA and Komodo APoW.

### Cited Findings
- **BCH EDA (Aug 1 to Nov 13, 2017)**: compares MTP(tip) with MTP(tip−6). If the gap > 12 h (normal ≈ 1 h), target += target/4, i.e. a 20% difficulty drop. Because MTP lags, several consecutive adjustments are expected. The author noted it needs ~92% abrupt hashrate loss to trigger and enough blocks to move the MTP. — [Bitcoin ABC review D298](https://reviews.bitcoinabc.org/D298); [commit "Add a difficulty adjustement mechanism in case of abrupt hashrate loss"](https://reviews.bitcoinabc.org/rABC7ad1105f43d7bff158d4b5c882ab9bf1b74d6cce)
- EDA outcome: "instabilities in mining difficulty ... resulting in Bitcoin Cash being thousands of blocks ahead of Bitcoin". Replaced by the 144-block cw-144 DAA at block 504032 (Nov 2017). — [Wikipedia (Bitcoin Cash/SV page)](https://en.wikipedia.com/wiki/Bitcoin_SV); BitMEX Research analysis PDF: [2017-11-16 BitMEX](https://blog.bitmex.com/wp-content/uploads/2017/11/2017.11.16-The-implications-for-Bitcoin-of-the-new-bitcoin-cash-difficulty-adjustment.pdf)
- The cw-144 replacement itself showed "a worrisome resonant hashrate oscillation with a period of 144 blocks". — [Harding 2020](https://github.com/chain2/chain2/blob/master/specifications/rtt.pdf); [zawy12 #48](https://github.com/zawy12/difficulty-algorithms/issues/48)
- **Bitcoin testnet 20-minute rule**: a block with timestamp > prev + 20 min may use min difficulty (0x1d00ffff), except the first block of a period. In testnet3 the retarget base was the last block of the period. If that was a min-diff block, the next period was constrained to diff 1..4, causing "block storms" (years of blocks mined in weeks). BIP94 (testnet4, assigned 2024-05-27) keeps the rule but takes the base from the *first* block of the previous period. It adds a time-warp rule: first block of a period nTime ≥ prev − 600 s. — [BIP 94](https://github.com/bitcoin/bips/blob/master/bip-0094.mediawiki)
- Testnet4 exploitation: PR #34420 (opened 2026-01-27, closed unmerged 2026-04-15) says CPU miners race to broadcast difficulty-1 blocks the instant the 20-min rule allows, ~85-90% of blocks. ASIC blocks were ~1 h apart, and a reviewer estimated ~30,000 more blocks than intended. Alternatives discussed: soft fork rejecting any block stamped > 20 min after its parent (PR #35081, also closed), and miners stamping 2 h ahead. — [bitcoin/bitcoin #34420](https://github.com/bitcoin/bitcoin/pull/34420); mailing list (March 2025, Sjors Provoost): [bitcoindev](https://gnusha.org/pi/bitcoindev/C899E966-6444-41EC-B977-96CFFCBF936A@sprovoost.nl)
- Mechanism of abuse in general: the rule keys on the miner-chosen timestamp, so a block can be stamped ≥ prev + 20 min (allowed since FTL = 2 h) and released as soon as that time is within FTL. Time-keyed relief plus a large FTL means relief on demand. — [zawy12 #30](https://github.com/zawy12/difficulty-algorithms/issues/30); [BIP 94](https://github.com/bitcoin/bips/blob/master/bip-0094.mediawiki)
- Safer variants: zawy's long-delay rule (−10% per T only after 6T + FTL) — [zawy12 #36](https://github.com/zawy12/difficulty-algorithms/issues/36). Komodo APoW activates only after (max backdating + max future leniency + margin), then decays exponentially — [Komodo APoW](https://komodoplatform.com/adaptive-proof-of-work/).
- Dash's testnet rule inherited by this fork (local code, `src/pow.cpp`): if new block time > prev + 2 h → powLimit; if > prev + 4·T → prev target × 10 (difficulty /10). This is gated by `fPowAllowMinDifficultyBlocks` (testnet/devnet only). The comment says "10 minutes" because Dash's T is 150 s, but here 4·T = 288 s (local source inspection).

### Inferences
- Porting Dash's testnet rule to mainnet as-is would be a textbook exploit at this chain's FTL. With FTL = 7200 s, any miner can stamp prev + 4·T = 288 s (or + 2 h) and release once that time is inside the FTL window. That yields 10x easier blocks (or powLimit) on demand, and the next DGW calculation averages that target in. This repeats the testnet3/EDA failures.
- A defensible emergency rule needs: (1) FTL reduced first (≲ a few T); (2) relief that is continuous and modest per T (e.g. ×0.9 per T beyond threshold), not a step to powLimit; (3) the DAA base and chainwork use the un-relieved ("official") target, as in TSA, so emergency blocks don't poison the averaging window; (4) a threshold > FTL + expected max honest delay. For the 99%-drop case, expected first block at 1% hashrate is 100·T = 7200 s. A rule starting at e.g. 6T + FTL (= 432 + FTL s) with −10%/T reaches ~1/100 difficulty after ~44 T beyond threshold (0.9^44 ≈ 0.0097). So the block arrives within ~an hour instead of ~2 h, and faster still once difficulty falls below the remaining hashrate's level (arithmetic based on zawy's formula; not simulated).

### Gaps
- Exact BCH EDA C++ (`pow.cpp`) was not retrieved; parameters come from the review discussion and Wikipedia (consistent with each other).
- No quantitative data found on how much EDA-period gaming profited specific pools.

## 5. Timestamp security requirements and their interaction with responsive DAAs

### Takeaway
Every responsive or real-time DAA is only as safe as its timestamp rules. The consensus of the sources (zawy, Harding, Bissias, BIP94) is: monotonic timestamps instead of MTP-11, an FTL that is a small fraction of the averaging window (and ≪ T for RTT), peer time removed or capped at ≤ FTL/2, and no timespan clamps (they enable the classic DGW/Digishield timestamp attacks). This fork's FTL of 7200 s is 100·T and ~4.2x the whole DGW window (24·72 = 1728 s), far outside every recommendation.

### Cited Findings
- Max single-block difficulty drop from a forward stamp: next_D = avg_D·1/(1 + FTL/(T·N)). Recommendation: FTL < N·T/10 for < 10% manipulation. — [zawy12 #30](https://github.com/zawy12/difficulty-algorithms/issues/30). Earlier: FTL ≤ 6T, and later "FTL be set to 300 or T·N/20, whichever is larger". — [zawy12 #13 Handling Bad Timestamps](https://github.com/zawy12/difficulty-algorithms/issues/13)
- zawy's 2023 rules (citing Lamport 1978): (1) no peer time, only local time; (2) monotonic timestamps instead of MTP; (3) FTL a fraction of block time; (4) enforcement precision slower than propagation delay; (5) no timespan limits. Miner rule: timestamp = max(local time, parent + 1 s), not released until within local time + FTL. FTL < ~5% of N·T. If peer time is kept, cap its error at FTL/2. BTC's 70-min revert is a hard constant that becomes Sybil-exploitable if FTL is lowered below ~70 min without changing it. — [zawy12 #76](https://github.com/zawy12/difficulty-algorithms/issues/76) (2023-05-14)
- Timespan limits with non-monotonic timestamps let a >50% attacker mine unlimited blocks in ~2.8x the averaging window. zawy says 5 coins had to fork to recover thousands of blocks. DGW and KGW coins are listed as vulnerable. — [zawy12 #76](https://github.com/zawy12/difficulty-algorithms/issues/76); [zawy12 #30](https://github.com/zawy12/difficulty-algorithms/issues/30); [zawy12 #31](https://github.com/zawy12/difficulty-algorithms/issues/31)
- Soft selfish-mining defense (no consensus change): don't accept a block for ln(2)·T if its timestamp is > +10 s ahead of or > −15 s behind local time when first seen. It assumes clocks within ±5 s and propagation ≤ 5 s. "Bitcoin could still stop most selfish mining profits if the clock error allowed is +/- 30 seconds". zawy notes it also lowers the barrier for RTT. — [zawy12 #76](https://github.com/zawy12/difficulty-algorithms/issues/76)
- Unsolved: the "FTL network split" (Culubas) attack. A miner stamping exactly at the FTL edge splits honest nodes. With 25% hashrate the attacker's tip gets 25% + 75%/2 = 62.5%. — [zawy12 #30](https://github.com/zawy12/difficulty-algorithms/issues/30)
- Peer-time timejacking: Culubas recommended a peer-time revert ≈ FTL/4. Zcash disabled peer time by default and constrained 25 min peer adjust + 90 min MTP-based FTL < 120 min. — [zawy12 #30](https://github.com/zawy12/difficulty-algorithms/issues/30)
- For RTT specifically: "2·err + FTL must be small compared to the time the RTT is significantly changing the difficulty". With RTT, "FTL << block time". — [zawy12 #30](https://github.com/zawy12/difficulty-algorithms/issues/30). Harding: max timestamp = "now", t_n > 0 — [Harding 2020](https://github.com/chain2/chain2/blob/master/specifications/rtt.pdf). Radium: discard headers whose timestamp differs from local time by more than ~max header propagation delay (NTP assumed for honest miners) — [Bissias 2020](https://arxiv.org/pdf/2007.05991).
- Merge-mining timestamp issue: lazy MM pool code may keep the parent's timestamp in new child templates, giving same or out-of-sequence stamps. — [zawy12 #35 Merge Mining Problems](https://github.com/zawy12/difficulty-algorithms/issues/35)
- Testnet4 added a time-warp rule (first block of period ≥ prev − 600 s) on top of MTP. — [BIP 94](https://github.com/bitcoin/bips/blob/master/bip-0094.mediawiki)

### Inferences
- For this chain (T=72, DGW N=24): zawy's formula with FTL = 7200 gives 1/(1 + 7200/1728) ≈ 0.19. A forward stamp could push difficulty to ~19% in one block, bounded in DGW by the 3x timespan clamp, so to ~1/3. Under the "FTL < N·T/10" rule the FTL should be ≲ 173 s with N=24, or ≲ ~360-720 s if moving to an EMA/LWMA with N≈50-100. For any RTT/TSA, FTL should be ≲ T/4..T (≈ 18-72 s), with peer-time cap ≤ FTL/2 (or removed) and monotonic timestamps.
- Lowering FTL is a consensus-relevant change for AuxPoW pools: their child-header nTime must track real time closely. Pools that reuse stale timestamps (zawy #35) would see more rejections.
- Order of operations implied by all sources: (1) fix timestamps (FTL, monotonicity, peer-time cap); (2) replace DGW with a well-behaved filter (WTEMA/ASERT/LWMA, no clamps); (3) only then add a real-time layer (TSA-style fast-over-slow, or a long-delay decay) to get fast post-drop recovery. Adding a responsive or emergency rule on top of FTL = 2 h repeats the EDA/testnet failure mode.

### Gaps
- No source quantifies the orphan-rate cost of FTL ≈ T for chains with T ≈ 1 min and merge-mining template latency. This would need simulation (the repo's Rust difficulty lab).
- No source evaluated RTT/TSA specifically under AuxPoW, where the parent pool controls template refresh.
